Touchpad · Gestures

Three-finger swipes, wired into KWin

Plasma 6.7's Touchpad panel has no gesture-assignment tab — checked directly on this machine. The real, verified path: a small gesture daemon that reads raw 3-finger swipes and fires KWin's existing global shortcuts over D-Bus.

Fedora Linux KDE Plasma 6.7.4 Wayland session libinput 1.31.3 Elan Touchpad detected

What you're setting up

Each swipe calls a KWin action that already exists as a global shortcut — confirmed working on this machine via busctl --user call org.kde.kglobalaccel. The gesture daemon just supplies the missing "3-finger swipe → run this command" trigger.

Swipe up Overview

Zooms out to all windows and desktops at once — the fastest way to jump between what's open.

Swipe down Minimize all (animated)

Minimizes every window with a real shrink-to-taskbar animation; repeat the swipe to bring them back. Deliberately not KDE's "Show Desktop" — that action has no animation in current KWin at all, by design, regardless of settings (see the callout below).

Swipe left Previous window

Cycles window focus backward, Alt+Tab-style — including unminimizing a hidden window if that's the one it lands on. Deliberately not a virtual-desktop switch (see the constraint below).

Swipe right Next window

Cycles window focus forward, mirroring the left swipe.

Setup

One step needs sudo and a logout — everything after that is already done or is a plain config file.

  1. Add yourself to the input group, then log out.

    Reading raw gesture events from /dev/input requires it: sudo usermod -aG input $USER. This is the one step that needs your password — nothing else here does. Log out and back in (or reboot) for it to take effect.

  2. Install libinput-gestures.

    Not in the Fedora repos — it's a small script from GitHub: git clone https://github.com/bulletmark/libinput-gestures.git && cd libinput-gestures && sudo make install. It depends on python3 and the libinput CLI, both already on this system.

  3. The config is already written.

    ~/.config/libinput-gestures.conf maps 3-finger up/down/left/right to Overview, MinimizeAll (animated), and window-focus previous/next. Each line runs the exact busctl --user call org.kde.kglobalaccel … command verified against this KWin session — nothing to fill in.

  4. Start it.

    libinput-gestures-setup start to run now, then libinput-gestures-setup autostart so it launches on login.

  5. Swipe to test.

    Rest three fingertips together before moving them — libinput needs genuine simultaneous contact to tell a gesture from a scroll.

Confirmed final state

All four directions tested working with a real touchpad gesture — not just a D-Bus dry run. Overview (up), MinimizeAll (down), and window-focus cycling (left/right) all fire correctly, and the earlier concern — that the native, hardcoded 3-finger desktop-switch gesture might fire alongside the new left/right window-focus mapping — was confirmed resolved.

The daemon install needed your sudo password — this session never had that, so it waited for you to run install-gestures.sh yourself. Confirmed afterward via libinput-gestures-setup status: installed, running, autostarting, using this exact config.

Two real limitations worth knowing

Left/right only stays desktop-switch-free with exactly 1 virtual desktop
KWin's native 3/4-finger desktop-switch gesture is hardcoded with no config toggle at all — confirmed by reading KWin's own source (virtualdesktops.cpp). It only has a visible effect if the desktop grid is more than 1 wide or tall. At 1 desktop, both dimensions are 1, so it's silent. Add a 2nd desktop and the grid must grow one way or the other: 2 columns brings the desktop-switch conflict back on left/right; 2 rows brings a conflict on up/down instead, fighting Overview/MinimizeAll. There's no arrangement that supports 2+ desktops without a conflict on one axis — a real trade-off to accept, not a setting to find.
"Show Desktop" was deliberately not used for swipe-down
It has zero animation in current KWin, unconditionally — confirmed in source: it hides windows through a separate internal state that the squash minimize-animation effect never listens to. KWin ships an unused-by-default minimizeall script that toggles real per-window minimize instead, which squash does animate — enabled via kwriteconfig6 --file kwinrc --group Plugins --key minimizeallEnabled true plus a KWin reconfigure. That's what swipe-down actually calls.

If a gesture doesn't fire

Nothing happens on any swipe
Check libinput-gestures-setup status — if it's not "running", the daemon isn't attached. A common cause is skipping the input group step, which silently fails to open the device.
libinput-gestures-setup start says permission denied on /dev/input/eventN
The usermod -aG input step didn't take effect yet — group membership only applies to new login sessions, so log out and back in (checking with groups in a fresh terminal) rather than just re-running the command.
Three fingers drags a window instead of triggering a gesture
Turn off three-finger drag on the Touchpad panel's General tab (Tres dedos → Arrastrar) — it competes with gesture recognition.
Gestures trigger inconsistently
Land all three fingertips at once, then move — starting with two fingers and adding a third mid-motion reads as scrolling, not a gesture.
Left/right feel swapped
Swap the two gesture swipe left/right lines in ~/.config/libinput-gestures.conf and run libinput-gestures-setup restart — direction convention is a matter of taste.
Left/right also switches virtual desktops, not just window focus
You likely have a 2nd virtual desktop configured — see "Two real limitations worth knowing" above. Reduce back to 1 desktop (System Settings → Workspace Behavior → Virtual Desktops) to silence KWin's native gesture.

Going further

Any other KWin shortcut works the same way: list every bindable action with busctl --user call org.kde.kglobalaccel /component/kwin org.kde.kglobalaccel.Component shortcutNames, then drop its exact name into an invokeShortcut line — 4-finger sets, pinches, and click-gestures in libinput-gestures.conf all use the same pattern.

Not KWin-specific: since each line is just a shell command, a swipe can just as easily run xdotool, launch an app, or hit a browser shortcut — the daemon doesn't care what it's a gesture for.

Verified against this machine's live KWin session, 2026-09-08 through 2026-09-10 — kcm_touchpad's actual panel was screenshotted (no gesture tab), every action was fired over D-Bus and confirmed before being written down, and the final left/right/down remap was confirmed with a real physical touchpad gesture, not just a dry run.
