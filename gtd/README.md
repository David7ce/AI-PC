# GTD

The personal task-tracking system for this workspace itself — not for any
one project inside `categories/`. Entirely gitignored: this is working
state, not public template content.

Follows David Allen's **Getting Things Done** method (the standard this is
named after and modeled on), split into six files instead of one flat list
because each stage genuinely needs different handling:

| File | GTD stage | Holds |
|---|---|---|
| [`inbox.md`](inbox.md) | Capture | Anything unprocessed — dump it here first, sort it later |
| [`next-actions.md`](next-actions.md) | Next Actions | Single, concrete, doable-now steps |
| [`projects.md`](projects.md) | Projects | Outcomes needing more than one step, each with a defined "done" |
| [`waiting-for.md`](waiting-for.md) | Waiting For | Blocked on you, on `sudo`, on an external service — not actionable yet |
| [`someday-maybe.md`](someday-maybe.md) | Someday/Maybe | Not committed, not urgent, not forgotten either |
| [`done.md`](done.md) | Done | Completed archive, most recent first |
| [`workspace-projects.md`](workspace-projects.md) | Reference | Live snapshot of every repo under `~/Workspaces` — branch, git state, pointer to each project's own roadmap. Not one of GTD's core six, but a recognized seventh category (non-actionable material worth keeping ready-to-hand) |

`workspace-projects.md` is generated by
[`../categories/system-administration/workspace-status/check-workspace-status.sh`](../categories/system-administration/workspace-status/check-workspace-status.sh)
— re-run it rather than trusting a stale copy. It never summarizes a
project's own roadmap content, only points to the file — each project owns
its roadmap's format.

## Contexts

Next actions and projects can be tagged with a context matching the domain
taxonomy in [`../docs/taxonomy.md`](../docs/taxonomy.md) — `@development`,
`@design-art`, `@system-administration`, `@research-analysis`,
`@writing-education`, `@business-management`, `@engineering` — so "what
should I work on" and "what kind of work is this" use the same vocabulary
instead of two unrelated ones.

## The weekly review

GTD calls for a regular pass over the six action/status files: clear `inbox.md` to zero
(each item becomes a next action, a project, someday/maybe, or gets
deleted), check `waiting-for.md` for anything that's unblocked, and confirm
`next-actions.md` still reflects what's actually next. An agent asked to
"do a GTD review" should walk exactly this sequence.

## For agents

See [`../AGENTS.md`](../AGENTS.md) for when to read and update these files
during normal work — the short version: check `next-actions.md` and
`inbox.md` at the start of a session if the user doesn't give you a task,
and move items forward (inbox → actioned, next-action → done) as you
complete things rather than leaving the files stale.
